# II-01. XSS (Cross-Site Scripting): отражённый, сохранённый, DOM  

## 🎯 Цели
- Понять три основных типа XSS  
- Разобраться в DOM-based механике  
- Научиться блокировать XSS на уровне шаблонов и логики  
- Осознать важность контекстного экранирования  
- Узнать, почему CSP — дополнительная защита, а не основная  

---

## 📌 1. Определение XSS  
XSS — это внедрение произвольного JavaScript-кода в страницу, отображаемую жертве.

Злоумышленник получает возможность:

- выполнять свой JS в браузере пользователя,
- похищать cookie и токены,
- выполнять операции от имени пользователя,
- подделывать UI и формы,
- перехватывать ввод пароля (keylogging),
- превращать атаку в ATO (Account Takeover).

---

## 📌 2. Типы XSS

### 1. **Reflected XSS (отражённый)**  
Данные из URL → немедленно попадают в HTML → выполняются.

Пример:
```
https://site.com/?q=<script>alert(1)</script>
```

### 2. **Stored XSS (сохранённый)**  
Злоумышленник сохраняет вредоносный JS в БД → он отображается всем пользователям.

Наиболее опасен.

### 3. **DOM-based XSS**  
JS-код на странице небезопасно работает с DOM:

```
location.hash  
document.write  
innerHTML  
outerHTML  
insertAdjacentHTML  
```

DOM-XSS — самый частый тип в SPA (React/Angular/Vue).

---

## 📌 3. Источники данных (sources)
- location.search / location.hash  
- innerHTML значения  
- атрибуты HTML  
- JSON из API  
- параметры из postMessage  
- window.name  

## 📌 4. «Раковины» выполнения (sinks)
- innerHTML  
- eval  
- setTimeout("...")  
- document.write  
- new Function()  
- jQuery.html()  

---

## 📌 5. Правильные защиты
- autoescape в шаблонизаторе  
- контекстное экранирование  
- запрет опасных API (innerHTML)  
- CSP (Content Security Policy)  
- безопасная обработка URL-параметров  

---

## 📌 6. Блок про РФ
У XSS особый вес в РФ по причине:

- массового внедрения внутренних порталов и ЛК пользователей;  
- требований ЦБ к аутентификации и управлению сессиями;  
- огромного количества уязвимых гос-сервисов;  
- угроз ATO (подмена операций, заявки, финтех-транзакции).

# II-02. CSRF (Cross-Site Request Forgery)

## 🎯 Цели
- Понять механику CSRF  
- Научиться защищаться с помощью токенов  
- Разобраться, как работает SameSite  
- Понять, почему CSRF особенно опасен в банковских системах  

---

## 📌 1. Суть CSRF  
Атака, при которой злоумышленник заставляет браузер пользователя выполнить запрос **от его имени**, используя его cookie.

Важно:  
браузер *автоматически* отправляет cookies по домену → злоумышленник этим пользуется.

---

## 📌 2. Условия успешной CSRF
- у пользователя есть активная сессия  
- есть state-changing операция (например, перевод денег)  
- запрос можно сформировать сторонним сайтом  

---

## 📌 3. Защита

### 1. CSRF Tokens  
- уникальные  
- одноразовые  
- привязанные к сессии  

### 2. SameSite Cookies  
Режимы:  
- `Strict` — безопаснейший  
- `Lax` — по умолчанию безопасный  
- `None` — только с Secure  

### 3. Проверка Origin/Referer  
Только для HTTPS.

# II-03. SQL Injection

## 🎯 Цели
- Осознать, почему SQLi = смерть для приложения  
- Разобраться в механике инъекции  
- Научиться защищаться параметризованными запросами  
- Понимать blind SQLi и UNION-based техники  

---

## 📌 1. Механика SQLi  
Ошибка возникает, когда данные пользователя попадают в SQL-запрос **без параметров**.

Пример плохого кода:
```sql
"SELECT * FROM users WHERE name = '" + input + "'"
```

---

## 📌 2. Виды SQLi

- **Error-based**  
- **Union-based**  
- **Boolean-based blind**  
- **Time-based blind**  
- **Out-of-band**  

---

## 📌 3. Защита

- Подготовленные выражения (prepared statements)  
- ORM-safe API  
- Строгая валидация входных данных  
- Ограничение прав БД (минимальный доступ)  

---

# II-04. NoSQL Injection  

Возникает в MongoDB, Elasticsearch, Redis и т.п.

Примеры:
```
{ "$where": "this.password == '123'" }
```

Защита:
- строгое приведение типов  
- запрет `$where`  
- фильтр операторов  
- безопасные ORM  

---

# II-05. Path Traversal  

Атака через пути файлов:
```
../../etc/passwd
```

Признаки:
- приложение принимает путь от пользователя  
- не выполняет каноникализацию  
- не проверяет, что путь остаётся в разрешённой директории  

Защита:
- allow-list директорий  
- canonic path  
- chroot / sandbox  

---

# II-06. Command Injection  

Инъекция в shell-команды:
```
ping "8.8.8.8; rm -rf /"
```

Злоумышленник выполняет произвольную команду на сервере.

Защита:
- не использовать shell  
- использовать системные API  
- экранировать аргументы  
- ограничивать ОС-контекст (seccomp, no-new-privileges)  

---

# II-07. SSRF  

Атака, при которой сервер делает HTTP/SSH/FTP запросы от имени приложения.

Особенно опасно в облаках:
```
http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

Защита:
- allow-list хостов  
- запрет внутренних IP  
- DNS pinning  
- egress-фильтрация  

---

# II-08. SSTI (Server-Side Template Injection)

Злоумышленник внедряет выражения в шаблон:
```
{{ 7*7 }}
```

В некоторых шаблонизаторах → выполнение кода.

Защита:
- запрещать пользовательские выражения  
- использовать безопасный режим шаблонизатора  
- разделять данные и шаблоны  

---

# II-09. XXE  

Опасности:
- вытягивание файлов с сервера  
- DTD expansion → DoS  
- SSRF через XML  

Защита:
- отключить DTD  
- использовать безопасные XML-парсеры  

---

# II-10. File Upload уязвимости  

Риски:
- загрузка веб-шелла  
- MIME spoofing  
- polyglot файлы  
- RCE через графические библиотеки  

Защита:
- проверка содержимого  
- хранить файлы вне webroot  
- renaming + UUID  
- sandbox обработка  

---

# II-11. CORS Misconfiguration  

Типовая ошибка:
```
Access-Control-Allow-Origin: *
Access-Control-Allow-Credentials: true
```

Что приводит к:
- краже данных из приватного API  
- выполнению запросов от имени пользователя  

---

# II-12. HTTP Parameter Pollution  

Одинаковые параметры:
```
?role=user&role=admin
```

Фреймворки обрабатывают по-разному → обходы ACL.

---

# II-13. Cache Poisoning  

Риск:
- отравление CDN/прокси кэша  
- выдача вредоносного контента другим пользователям
