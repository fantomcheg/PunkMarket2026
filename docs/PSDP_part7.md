# 💼 Раздел V. Advanced Web Exploitation и бизнес-логика

Этот раздел раскрывает наиболее сложные и опасные уязвимости, которые:

- не ловятся SAST/DAST,
- не принадлежат классике OWASP Top 10,
- возникают из-за **ошибок проектирования**, а не синтаксиса,
- стоят компаниям (особенно российским финтех/банкам) миллионов рублей,
- часто приводят к фроду и убыткам.

Это — зона, где ломаются крупные продукты, а не студенческие pet-проекты.

---

# V-01. Business Logic Vulnerabilities (BLV)  

## 🎯 Цели  
- Осознать, что бизнес-логика — основной источник фрода  
- Научиться видеть избыточные/недостающие проверки  
- Понять разницу между XSS/SQLi и ошибками логики  
- Разобрать реальные сценарии атак  

---

## 📌 Что такое уязвимость бизнес-логики  
Это ошибка, возникающая, когда приложение:

- неверно трактует последовательность действий,  
- допускает неправильный порядок операций,  
- не ограничивает состояние,
- не учитывает повторные запросы,
- или слишком доверяет клиентской стороне.

BLV — это **ошибки в правилах бизнеса**, не в коде.

---

## 📌 Примеры  
### 1️⃣ Повторное использование купона  
```
POST /apply-coupon
```
— купон списывается из БД, но `used=true` выставляется **после** применения → можно отправить несколько параллельных запросов.

### 2️⃣ Изменение цены перед оплатой  
Frontend присылает price → злоумышленник меняет price локально → оплата проходит.

### 3️⃣ Снятие лимитов  
При создании операции сервера не проверяют лимиты пользователя → лимиты можно обойти изменением ID счёта.

### 4️⃣ Игнорирование негативных сценариев  
Приложение предполагает правильный порядок действий:
```
A → B → C
```
но злоумышленник делает:
```
B → C
```

# V-02. Race Conditions / TOCTOU  

## 🎯 Цели  
- Понять механику гонок в веб-приложениях  
- Изучить “фирменные” атаки параллельными запросами  
- Осознать риски TOCTOU: Time-of-check to time-of-use  

---

## 📌 Как возникают гонки  
- проверка и действие выполняются в разных местах  
- операция неатомарна  
- несколько запросов обрабатываются параллельно  

---

## 📌 Примеры  

### 🏦 1. Двойное списание денег  
Пользователь отправляет два параллельных POST-запроса.  
Проверка баланса выполнена дважды → деньги списываются дважды.

### 🎫 2. Двойная покупка билета  
Нет блокировки места → на одно место продают два билета.

### 🎁 3. Многократное получение бонуса  
```
/claim-bonus
```
Правильно:  
- выдавать бонус → обновлять состояние → атомарно.

---

## 📌 Защита  
- транзакции  
- optimistic/pessimistic locking  
- idempotency keys  
- очереди сообщений  
- атомарные операции в БД  
- запрет параллельных запросов на критичные операции

# V-03. Integer Overflow / Underflow  

Чаще встречается в:

- финансовых системах,  
- бонусных программах,  
- расчётах комиссии,  
- игровых экономиках,  
- криптосистемах.

Ошибка:  
значение превышает предел типа → переполнение → неверная логика.

---

# V-04. Floating Point Precision Issues  

Финтех/банки в РФ часто страдают от:

- округлений,
- арифметики double,
- расхождений при вычислениях комиссий.

Правильно:  
использовать Decimal/BigDecimal, фиксированную точность.

# V-05. Abuse & Fraud Scenarios  

Фрод — это именно **бизнес-логика + слабая архитектура**.

## Типичные сценарии:
- подбор ID (авиабилеты, финтех)  
- злоупотребление акциями («пригласи друга»)  
- обход платных функций  
- генерация повышенных лимитов  
- использование старых токенов  
- манипуляции временем (таймеры, дедлайны)  

---

# V-06. Replay Attacks  

Повторный запрос:
```
POST /transfer
```
если обработан дважды → двойной перевод.

Защита:
- nonce  
- one-time tokens  
- idempotency keys  
- отметка операций в хранилище

# V-07. Enumeration (логические утечки)  

## Примеры:
- различимые ответы «email существует / не существует»  
- различимые ответы при login  
- различимые ответы при reset password  
- различимые ответы при поиске

# V-08. Broken Access Control в бизнес-логике  

### Примеры:
- сотрудник может смотреть чужих клиентов  
- менеджер может изменять лимиты других отделов  
- обычный пользователь может выполнять действия premium-пользователя  

Чаще всего ломается из-за отсутствия централизованной модели.

# V-09. Проблемы согласованности состояния  

Ошибка:
```
состояние обновляется только на фронтенде
```
→ backend не проверяет реальное состояние.

# V-10. Anti-automation / Anti-bot  

## Проблемы:

- нет защиты от парсинга  
- нет защиты от массовых операций

- captcha

- throttling
