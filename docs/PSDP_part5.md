# 🔐 Раздел III. Аутентификация, сессии и контроль доступа  

Этот раздел охватывает всё, что связано с:

- проверкой личности пользователя,
- хранением состояния (сессии),
- правильным контролем прав доступа,
- защитой критичных потоков (логин, logout, reset password),
- ошибками бизнеса, приводящими к ATO (Account Takeover).

Это один из самых важных разделов курса, особенно для РФ — где требования по защите аутентификации лежат в ФЗ-152, требованиях ЦБ РФ и ГОСТ 56939–2024.

---

# III-01. Cookie-based сессии и флаги безопасности  

## 🎯 Цели
- Понять, как работает сессионный механизм  
- Научиться правильно выставлять cookie-флаги  
- Осознать риск кражи cookie и ATO  
- Научиться защищать сессию от XSS/CSRF  

---

## 📌 1. Что такое сессия  
Сессия = запись о состоянии пользователя на сервере.

Чаще всего идентификатор хранится в cookie:
```
Set-Cookie: sessionid=abc123;
```

---

## 📌 2. Флаги безопасности  

### **HttpOnly**
Запрещает доступ JS к куке.  
Основная защита от кражи cookie через XSS.

### **Secure**
Cookie отправляется только по HTTPS.

### **SameSite**
Контроль межсайтовой отправки:

- `Strict` — максимум безопасности  
- `Lax` — безопасно для большинства приложений  
- `None` — требует `Secure`, используется для SSO  

### **Path**, **Domain**
Минимизировать scope куки.

---

## 📌 3. Время жизни сессий  
- Короткое время для чувствительных операций  
- Idle timeout + Absolute timeout  
- Принудительная ротация (при логине/изменении пароля)

---

## 📌 4. Удаление сессии  
`Set-Cookie: sessionid=; Max-Age=0`

Требования:
- уничтожение на сервере  
- уничтожение на клиенте  
- журналирование события выхода  

---

# III-02. Сессионный hijacking и fixation  

## 📌 1. Session Hijacking  
Кража куки → вход в аккаунт жертвы.

Источники:
- XSS  
- незащищённый Wi-Fi  
- протокол HTTP  
- прокси  

Защита:
- HttpOnly  
- Secure  
- HSTS  
- короткие сессии  
- привязка к устройству/IP/фингерпринту  

---

## 📌 2. Session Fixation  
Злоумышленник заставляет пользователя использовать заранее известную ему сессию.

Пример:
```
https://site.com/login?sessionid=evil123
```

Защита:
- Регенерация sessionid при логине  
- Игнорирование sessionid из URL  
- Принудительный rotate при повышении прав  

---

# III-03. Восстановление доступа (Password Reset Flow)  

Один из самых взламываемых механизмов.

## 📌 Основные уязвимости:
- предсказуемые токены  
- бесконечный срок жизни токена  
- токен в URL логируется  
- отсутствие rate limiting  
- отсутствие проверки устройства  
- отправка токена в незашифрованном виде  
- отсутствие проверок личности (KYC-lite)  

---

## 📌 Требования к безопасности password reset:
- токен должен быть одноразовым  
- срок жизни ≤ 10–15 минут  
- токен должен быть непредсказуемым (128+ бит)  
- удаление токена после использования  
- логирование попыток восстановления  
- защита от enumeration (`Если email есть — мы отправили письмо`)  
- captcha / throttling при множественных попытках

# III-04. MFA и методы аутентификации  

## Типы MFA:
- TOTP (Google Authenticator)  
- Push-based (банковские приложения)  
- U2F/WebAuthn  
- SMS (самый слабый вариант)  

## Уязвимости MFA:
- SIM-swap  
- phishing MFA prompts  
- malware на телефоне  
- MITM-проксирование OAuth/SSO  

## Рекомендации:
- WebAuthn как «золото»  
- TOTP как «серебро»  
- SMS — только как fallback

# III-05. Access Control: RBAC, ABAC и IDOR  

Контроль доступа — самый частый источник уязвимостей в корпоративных системах.

---

## 📌 1. Типы контроля доступа  
### RBAC — Role-Based Access Control  
Роли: admin, user, manager

### ABAC — Attribute-Based Access Control  
Атрибуты: отдел, владелец ресурса, уровень классификации данных

### PBAC / Policy-Based Access  
Политики на уровне запросов и правил.

---

## 📌 2. Почему контроль доступа ломается чаще всего  
- проверки размазаны по коду  
- нет единой архитектуры прав  
- разработчики делают проверки «на глаз»  
- ID передаётся в URL без проверки владения  

---

## 📌 3. IDOR (Insecure Direct Object Reference)  
Классический пример:

```
GET /api/user/12345
```

Заменяем ID → получаем чужие данные.

Это самая частая уязвимость в реальных системах РФ.

---

## 📌 4. Защита от IDOR  
- проверка владельца ресурса  
- централизованная ACL  
- запросы должны проверять identity + ownership  
- не доверять frontend  
- не доверять client-side filtering  

---

# III-06. Привилегии, эскалация и модели прав  

## Типовые ошибки:
- скрыть кнопку «Удалить» в UI → значит пользователь **не может удалить**  
  (Неверно: backend должен проверять!)  
- логика: «если user.isAdmin, то…» по всему коду  
- отсутствие Deny-by-default  

---

## 📌 Принципы защиты:
- Централизованный PEP/PDP  
- Явные проверки прав в backend  
- Право должно храниться *рядом с ресурсом*, не в UI  
- Политика «минимально необходимых прав»  
- Логирование всех действий с высокими правами
