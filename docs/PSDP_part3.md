# Раздел I. Основы безопасной разработки  
Этот раздел формирует фундаментальные знания, без которых невозможен AppSec.  
Включает четыре ключевых темы:

1. **Валидация ввода и каноникализация**  
2. **Контекстное экранирование**

# I-01. Валидация ввода и каноникализация  

## 🎯 Цели урока  
- Понять, что входные данные *всегда недоверенные*  
- Научиться приводить данные к каноническому виду  
- Разобраться, почему валидация — не экранирование и не фильтрация  
- Узнать типичные обходы валидаторов и как их предотвращать  

## 📌 1. Почему валидация — основа безопасности  
Любая инъекция начинается с одного факта:

> «Приложение доверяет входным данным».

Уязвимости возникают, когда разработчик:
- допускает «грязные» пользовательские данные в бизнес-логику,
- выполняет операции без проверки,
- использует данные как часть пути, SQL-запроса, shell-команды, имени файла и т.п.

Это приводит к:
- SQL Injection  
- XSS  
- Path Traversal  
- Command Injection  
- SSTI  
- LDAP/NoSQL инъекциям  
- SSRF  
- и десяткам других CWE.

---

## 📌 2. Типы входных данных  
Все источники считаются недоверенными:

- HTTP query параметры  
- JSON body  
- form-data  
- cookies  
- HTTP headers  
- file uploads  
- значения из очередей/топиков Kafka/RabbitMQ  
- данные из других сервисов (внешних *и внутренних*)  
- параметры командной строки  
- содержимое файлов  

**Важно:**  
Даже внутренние микросервисы являются недоверенной стороной → возможны SSRF/host header атаки.

---

## 📌 3. Каноникализация  
Каноникализация = приведение данных к единому базовому представлению *перед* проверками.

Почему это важно?  
Потому что злоумышленники используют экзотические кодировки и формы данных:

- UTF-7  
- Overlong UTF-8  
- Unicode normalization (NFD/NFC/NFKD)  
- URL-encoding + двойное кодирование  
- смешивание кириллицы/латиницы  
- нулевые байты (`%00`)  
- пробелы разных типов  

### Пример:
Путь:
```
..%2f..%2fetc/passwd
```
и
```
%2e%2e/%2e%2e/etc/passwd
```
и
```
..\..\etc/passwd
```
и
```
%2e%2e%5c%2e%2e%5cetc/passwd
```

После каноникализации → все превращаются в одно и то же.

---

## 📌 4. Allow-list против deny-list  
**Правильный подход: ALLOW-LIST.**

Допустимые данные:
- конкретный набор символов  
- конкретный формат  
- конкретный тип  

Неправильный подход:
- «запретить опасные символы»  
- списки фильтрации (их всегда можно обойти)

---

## 📌 5. Типовые примеры безопасной валидации  

### Числа
```
if (!/^\d+$/.test(userInput)) reject();
```

### Email
RFC-совместимые валидаторы сложные → на практике:
- проверяем минимум структуру,  
- остальное проверяет бизнес-логика (например, отправка подтверждения).

### UUID
```
/^[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[1-5][0-9a-fA-F]{3}-[89abAB][0-9a-fA-F]{3}-[0-9a-fA-F]{12}$/
```

### Ограничение длины
Обязательное правило:
- любое поле ограничено максимальной длиной (даже если SQL/ORM не требует этого).  

---

## 📌 6. Где размещать валидацию  

### Правильный порядок:

1. **Приём данных** (до бизнес-логики)  
2. Каноникализация  
3. Валидация формата  
4. Только потом — бизнес-логика  

### Неправильный порядок:
- пропускать всё в бизнес-логику → проверять «когда понадобится»  
- проверять только на фронтенде  
- проверять только на уровне UI (HTML5 input constraints)

---

## 📌 7. Типичные ошибки разработчиков  

- Валидация сделана только на frontend  
- Используются «чёрные списки»  
- Нет ограничения длины строк  
- Нет нормализации путей  
- Разрешены wildcard-паттерны без проверки  
- В ORM позволяется выполнять «сырые» запросы  
- Разработчик считает внутренние сервисы безопасными  

---

## 📌 8. Чек-лист (валидация)

- [ ] Все входные данные считаются недоверенными  
- [ ] Валидация выполняется *на сервере*  
- [ ] Выполнена каноникализация  
- [ ] Используется allow-list подход  
- [ ] Проверены тип, структура, диапазон  
- [ ] Проверена максимальная длина  
- [ ] Все ошибки валидации → одинаковые безопасные ответы

# I-02. Контекстное экранирование  

## 🎯 Цели урока  
- Понять, что экранирование зависит от контекста  
- Научиться защищать каждый контекст (HTML, JS, URL, CSS)  
- Разобраться, почему универсальных фильтров не существует  

---

## 📌 1. Контексты в вебе  

### HTML  
```
<div>{{ userInput }}</div>
```

### HTML Attribute  
```
<a href="{{ userInput }}">
```

### JavaScript  
```
<script>var x = "{{ userInput }}";</script>
```

### URL  
```
<a href="/search?q={{ userInput }}">
```

Каждый контекст требует своего способа экранирования.

---

## 📌 2. Принципы контекстного экранирования  
- В HTML-текст исключаем `<`, `>`, `"`, `'`  
- В JavaScript экранируем `\`, `"`, `'`, newlines  
- В URL выполняем `encodeURIComponent()`  
- В HTML-атрибутах — экранирование + проверка протокола (https/http/mailto)  

---

## 📌 3. Почему XSS возникает даже при фильтрах  

Плохой фильтр:
```
replace("<", "")
```
Обход:
```
<svg/onload=alert()>
```

Фильтры никогда не догоняют атакующего.

---

## 📌 4. Правильный подход  
Использовать:

- шаблонизаторы с autoescape  
- библиотеки экранирования  
- запрещённые контексты (innerHTML, dangerouslySetInnerHTML)

# I-03. Ошибки и утечки информации  

Типовые проблемы:

- Stack trace в ответе  
- Детальный текст ошибки  
- Ошибки авторизации/аутентификации растеклись по логам  
- Выдача внутренних идентификаторов  
- Диагностика продакшена в проде  

---

# I-04. Безопасное логирование  

Основные принципы:

1. Не логировать пароли, токены, cookie, ключи  
2. Маскировать PII (телефоны, email, ФИО)  
3. Логи должны быть неизменяемыми  
4. Логи должны быть централизованы  
5. Ошибки должны быть безопасны для пользователя
