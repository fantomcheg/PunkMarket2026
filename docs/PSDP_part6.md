# 🔗 Раздел IV. Современные протоколы и API

Современные веб-приложения почти всегда используют:  
- токены (JWT),  
- OAuth2 и OpenID Connect,  
- SSO интеграции,  
- GraphQL,  
- WebSockets,  
- SPA/мобильные клиенты.  

Ошибки в этих протоколах приводят к захвату аккаунтов, краже токенов, подмене сессий, эскалации прав и утечкам данных.

Этот раздел — критичен для больших корпоративных систем РФ: банки, финтех, телеком, госуслуги, КИИ.

# IV-01. JWT: архитектура, структура, риски и правильная проверка  

## 🎯 Цели
- Понять, как устроен JWT  
- Научиться корректно проверять подпись и claims  
- Разобрать все типовые ошибки разработчиков  
- Узнать про kid-инъекции, alg=none и подмену ключей  

---

## 📌 1. Структура JWT  
```
header.payload.signature
```

### Header
- alg — алгоритм  
- typ — тип  

### Payload (claims)
- sub — идентификатор пользователя  
- iat — время выпуска  
- exp — срок действия  
- iss — кто выдал  
- aud — кому предназначен  

### Signature  
HMAC или RSA/ECDSA подпись.

---

## 📌 2. Типовые ошибки разработчиков  

### ❌ 1. Непроверенный alg  
Если сервер доверяет `alg=none` → токен можно подделать.

### ❌ 2. Проверка только подписи, без claims  
Обычная ошибка:

- подпись валидная → всё хорошо  
- но `exp` истёк  
- или `aud` не совпадает  
- или `iss` подделан  

### ❌ 3. Путаница при загрузке JWK по `kid`  
Пример атаки:

- злоумышленник подсовывает `kid=evil`  
- сервер автоматически скачивает JWK  
- злоумышленник подменяет ключ → получает валидные токены  

### ❌ 4. Слишком длинный срок жизни  
Нельзя выдавать токены на месяцы.

### ❌ 5. Хранение JWT в localStorage  
→ XSS = моментальный ATO.

---

## 📌 3. Правильная проверка токена (золотой стандарт)  

1. Проверить **подпись**  
2. Проверить **exp**  
3. Проверить **nbf**  
4. Проверить **aud**  
5. Проверить **iss**  
6. Проверить **scope/roles**  
7. Проверить **revocation** (через хранилище отозванных токенов)

---

## 📌 4. Где хранить JWT?  

### ❌ Нельзя в localStorage  
Причина: XSS = кража токена.

### ✔ Правильно  
Хранить **в HttpOnly+Secure cookie**.

# IV-02. Уязвимости JWT: alg=none, key confusion, kid injection  

## 📌 1. alg=none  
Токен без подписи → сервер должен отклонять.

## 📌 2. HMAC/RSA Key Confusion Attack  
Если сервер неверно определяет алгоритм, можно заставить его использовать публичный ключ как секрет HMAC.

## 📌 3. KID injection  
Вставка пути:
```
"kid": "../../../../etc/passwd"
```

Если сервер использует `kid` как путь — это RCE/утечка.

# IV-03. OAuth2 / OpenID Connect  

## 🎯 Цели
- Разобрать роли: client, resource owner, authorization server  
- Понять потоки: Authorization Code, PKCE, Implicit, Client Credentials  
- Узнать типовые уязвимости OAuth  
- Научиться защищать redirect_uri  

---

## 📌 1. Потоки OAuth2  

### 1. Authorization Code  
Используется веб-приложениями.  
**Всегда с PKCE** (иначе возможно перехватить код).

### 2. Implicit  
⚠ Устаревший и НЕ БЕЗОПАСНЫЙ.  
Использовать нельзя.

### 3. Client Credentials  
Межсервисный обмен.

---

## 📌 2. OpenID Connect (OIDC)  
Расширение OAuth для аутентификации пользователя:

- id_token (JWT)  
- userinfo endpoint  

---

## 📌 3. Уязвимости OAuth  

### 1️⃣ Open Redirect → Token Theft  
Если `redirect_uri` не фиксирован → токен можно увести через свою страницу.

### 2️⃣ mix-up attack  
Смешение клиентов → выдача токена другому приложению.

### 3️⃣ token leakage через Referer  
Если токен в query → он утечет в третьи ресурсы.

### 4️⃣ PKCE bypass  
Неправильная проверка challenge.

---

## 📌 4. Защита OAuth/OIDC  

- фиксированный `redirect_uri`  
- обязательный PKCE  
- запрет Implicit потока  
- хранение токенов только в HttpOnly cookie  
- проверка nonce/state  
- короткие сроки жизни токенов  

---

# IV-04. Refresh-token, ротация, токен-ревокация  

## ❗ Самая частая ошибка в крупных компаниях РФ  
Использование refresh-токена «пожизненно».

Это приводит к:
- компрометации аккаунтов  
- масштабным утечкам  

---

## Правильная модель:
- RT хранится в HttpOnly cookie  
- RT одноразовый (rotating refresh tokens)  
- RT валиден 24–72 часа  
- компрометация → автоматический revoke всей цепочки

# IV-05. GraphQL Security  

## 🎯 Цели  
- Понять surface attack GraphQL  
- Изучить запросы глубокой/сложной структуры  
- Научиться защищать GraphQL от DoS и BOLA  

---

## 📌 1. Проблемы безопасности GraphQL  

### 1️⃣ Overfetching / Underfetching  
Запрос вытягивает слишком много данных.

### 2️⃣ Интроспекция  
Выдача всей схемы злоумышленнику.

### 3️⃣ Expensive queries  
Можно создать запрос, который загрузит базу.

### 4️⃣ BOLA (IDOR)  
GraphQL особенно уязвим к контролю доступа.

---

## 📌 2. Защита GraphQL  
- depth-limit  
- complexity-limit  
- отключение интроспекции в проде  
- строгий ACL на уровне резолверов  
- rate limiting  

---

# IV-06. WebSockets: аутентификация и авторизация  

## 📌 Атаки против WebSockets:
- подключение без авторизации  
- перехват токена в query-string  
- подделка сообщений  
- отсутствие перегородки между room/channel  

---

## 📌 Защита WebSockets  
- Авторизация → только через cookie  
- Проверка токена на handshake  
- ACL на уровне сообщений  
- Ограничение каналов и комнат
